## Код — race condition / корректность

- [x] `/ui/delete` проверяет `_INGEST_STATE.get("running")` **без** `_INGEST_LOCK`
  (в отличие от `_run_index_job_background`, где та же проверка под локом) — параллельные
  rebuild и delete могут одновременно тронуть `manifest.json`/индекс.
  `mcp_http.py:3183` vs `mcp_http.py:667-676`. **Исправлено**: добавлен разделяемый
  `_exclusive_job()` (async context manager, check-and-set под `_INGEST_LOCK`,
  `mcp_http.py:368-392`), применён к `/ui/delete`, `/ui/wipe`, `/ui/clean-orphans` и
  `/ui/clear-incoming` (у последнего вообще не было busy-проверки — добавлена).
  Добавлены регрессионные тесты `tests/test_mcp_http.py`
  (`test_destructive_ui_endpoints_busy_when_job_running`,
  `test_ui_delete_releases_exclusive_job_state_after_success`). Полный прогон:
  283/283 passed, ruff чист.
- [x] Фикс "stale rebuild lock" (`7b65315`) даёт ложный "stale" и молча снимает лок, если
  `manifest.json` был перезаписан `delete_documents`/`clean_orphans` после упавшего rebuild —
  баннер о незавершённом rebuild пропадает без реального решения проблемы. Не покрыто тестами.
  `mcp_http.py:1851-1877`. **Исправлено**: staleness больше не зависит от `manifest.json`
  вообще. `_run_index_job_background` теперь при успехе пишет `<lock>.done` с тем же
  `lock_ts`, что и в `.rebuild.lock`, прямо перед удалением самого лока (`mcp_http.py:705-761`);
  `_ui_status_payload` считает лок stale только если `.done`-маркер существует и его
  timestamp совпадает с локом (`mcp_http.py:1895-1926`) — то есть именно этот запуск
  подтверждённо завершился, а не "манифест кто-то потрогал". Добавлены 4 регрессионных
  теста в `tests/test_mcp_http.py`, включая прямое воспроизведение бага (unrelated
  manifest write больше не сбрасывает баннер). Побочно найден **отдельный баг**:
  `lock_path`/`.done` строятся через `_root_dir()` напрямую, **без** учёта `DOC_RAG_ROOT`
  (в отличие почти от всех остальных путей в файле, которые делают
  `os.environ.get("DOC_RAG_ROOT") or _root_dir()`) — `mcp_http.py:706,1904` (номера строк
  до этого фикса). На текущем проде совпадает случайно (editable-install source ==
  `DOC_RAG_ROOT`), но если их когда-нибудь разведут — лок начнёт писаться не в тот
  каталог. **Не исправлено** — отдельный от текущей задачи баг, вынесен ниже отдельным
  пунктом на согласование.
- [x] "Rebuild одного документа" на деле делает **полный** переэмбеддинг всего корпуса, а не
  инкрементальный — на CPU-only сервере дорого и не то, что ожидается от кнопки по названию.
  `pipeline.py:1391-1407` (`rebuild_docs`). **Исправлено**: вместо `vi.reset()` +
  `vi.build(all_chunks, force=True)` теперь `vi.delete(target_ids)` (убрать старые векторы
  пересобираемых документов) + `vi.build(all_chunks, force=False)` — `VectorIndex.build()`
  уже умеет инкрементально доэмбеддивать только отсутствующие в индексе `chunk_id`
  (`vector_index.py:115-167`), это просто не использовалось. При пустом индексе
  `force=False` эквивалентен полной сборке (проверяется `store.size > 0`), так что
  поведение для первого построения не меняется.

  **Побочно найден и тоже исправлен более серьёзный баг**: `doc_id` в `rebuild_docs`
  пересчитывается из хэша содержимого файла — если контент реально изменился, новый
  `doc_id` отличается от старого, а старые записи под старым `doc_id` никогда не убирались
  из `chunks.jsonl` (только `.md`-файл чистился). Эти orphan-чанки участвовали в построении
  индекса и **бессрочно засоряли поиск устаревшим содержимым** после каждого содержательного
  обновления документа через rebuild-docs. Старый комментарий в коде ("previous rebuild_docs
  calls may have added chunks not in the index") — по факту описание симптома этого же бага,
  "лечившееся" полным ре-эмбеддингом (что удерживало индекс согласованным с мусором, но не
  убирало сам мусор). Исправлено: `all_chunks` теперь фильтруется по `doc_id`, реально
  присутствующим в финальном `all_docs`, перед дедупом и записью (`pipeline.py`, Phase 2
  merge). Не тронуты (отдельный, менее критичный follow-up): orphan-файлы
  `build/blocks/<old_doc_id>.jsonl` и `build/quality/<old_doc_id>.json` по-прежнему не
  чистятся — это уже не про поиск, а про мусор на диске.

  3 новых теста в `tests/test_dedup.py`: `test_rebuild_docs_only_reembeds_target_document`,
  `test_rebuild_docs_drops_orphaned_chunks_when_content_hash_changes`. Полный прогон:
  289/289 passed, ruff чист.
- [x] `faiss_store.py delete()` — `if cid in ids` по `list[str]` — линейный поиск O(n·m),
  деградация с ростом корпуса при множественном delete. `vectorstore/faiss_store.py:159-161`
  **Исправлено**: `ids_set = set(ids)` перед циклом.
- [x] `faiss_store.py delete()` — `np.vstack([...reconstruct(p)...])` держит список векторов
  + результат одновременно — временное удвоение памяти при удалении даже одного документа
  из большого индекса (bge-large, dim=1024, сотни тысяч чанков → сотни MB). `faiss_store.py:175`
  **Исправлено**: `np.empty((len(keep_positions), dim))` + запись `reconstruct()` напрямую
  в готовый массив по индексу, без промежуточного списка и `vstack`. Поведение
  byte-for-byte идентично — весь набор `tests/test_faiss_reconstruct.py` (сверяет векторы
  побайтово после prune) прошёл без изменений.
- [x] `vector_index.py _encode` — эксп. backoff ретраит с тем же большим батчем; если причина
  сбоя — OOM на полном корпусе, ретрай не поможет и трижды повторит зависание. `vector_index.py:90-113`
  **Исправлено**: `batch_size`, передаваемый в `embedder.encode()`, теперь делится пополам
  на каждой повторной попытке (`max(1, batch_size // 2)`) вместо повторного использования
  того же значения — целится в реальный сценарий OOM (конкретный мини-батч внутри
  `sentence-transformers` слишком большой для доступной памяти). 2 новых теста в
  `tests/test_vector_index.py`: `test_encode_retries_with_shrinking_batch_size`,
  `test_encode_raises_after_exhausting_retries`. Полный прогон: 291/291 passed, ruff чист.

  `Path(__file__).resolve().parents[3]`), а не через паттерн

  `build/manifest.json` — сам механизм детекции останется внутренне непротиворечив
  (пишет и читает по одному и тому же неверному пути), но физически "потеряется".
  На проде сейчас совпадает случайно. Нужно решить: поправить на общий паттерн.

- [ ] (follow-up, не критично) `rebuild_docs` при смене `doc_id` (контент реально изменился)
  не чистит `build/blocks/<old_doc_id>.jsonl` и `build/quality/<old_doc_id>.json` — мусор
  на диске, не влияет на поиск (в отличие от исправленных orphan-чанков выше). Можно
  почистить заодно с `clean_orphans`, если он туда не заглядывает.
